# 密码标准对齐实施计划

日期：2026-10-17。对象：团队 PFDAM 方案与当前 V4.2 电网数据协同应用系统。状态：已形成研发计划，各阶段尚待实施；本次规划不改变密码内核、信任机制或运行配置。

本轮优先补强密码的使用和管理：明确保护对象与适用标准，完善身份与审计，建立密钥生命周期和可信公钥登记，再保护重要存储数据与 UC 结果声明。标准消息、密码设备及部署互通按实际场景接入。推进依据为[标准对齐分析](STANDARDS_ALIGNMENT.md)与[37 项工程对照](../references/standards/20261017/alignment.json)，阶段和责任映射保存在[可检查的计划清单](STANDARDS_ALIGNMENT_PLAN.json)。

## 保护目标和本轮范围

我们要让系统能够回答：哪些数据由谁保护，使用什么算法和参数，谁能使用或更换密钥，公钥为什么可信，异常时是否停止输出，以及评审人员如何复核这些结论。

| 层次 | 本轮目标 | 完成依据 |
|---|---|---|
| 算法和协议使用 | 核对真实实现、参数、编码、身份绑定、签名组合和传输约束 | 正式文本、向量、边界测试及可重现互通记录分别留证 |
| 应用系统工程 | 密钥、身份、存储、审计、历史验证和恢复形成闭环 | 正常流程及越权、篡改、撤销、故障等反例均有实际记录 |
| 模块和产品 | 界定自研适配层、软件库及外部产品的职责；需要时真实对接 | 产品及模块的边界、版本、适用证明和对接实测，不能由库名称代替 |
| 真实部署和正式评估 | 确定部署对象后补齐物理环境、网络、岗位和制度执行 | 实际部署证据及相应正式评估；本地研发自检不能代替 |

23 份材料包含 5 项主要对照、6 项产品或接口相关标准、12 项当前未涉及标准。37 项是工程观察项，并非全部标准条款。39786 第三级条款仅作差距参考，当前没有确定或取得该等级。适用性仍需在部署对象确定后复核；不能把“当前未涉及”改成“已符合”，也不计算标准符合率。

保留以下约束：

- PFDAM 是团队自己的前期研究方案。本轮保留数学构造、P0 与 P1 的区分及已确认限制；标准外层加固不代替参数安全论证。
- 正常业务最低为 SAB：ECDSA 与 ML-DSA-65 必须同时验证，两类业务链路均检查实际协商的 X25519MLKEM768。增强模式保留额外 SM2 签名与 TLS 内 SM4-GCM，不作自动降级。
- GW 不能加载 Source 原始明文、UC 秘密和私有真值。REAL、PREVIEW、REPLAY 保持显式标记。
- 改变签名字段、上下文或信任语义必须新增版本；V1、V2、V3 历史验证及原始证据保留。旧归档不会被自动重签或升级为新的安全保证。
- 最终提交材料、录像彩排、发布打包和远程上传继续暂停。Linux 与 WSL 仍是初始执行平台。

## S0 标准和保护对象登记

责任类别：方案分析与工程架构。主要落点为标准登记、研发文档和后续只读自检展示。

1. 为每个保护对象登记数据流、拥有角色、机密性、完整性、真实性需求及信任边界。覆盖 Source 数据、授权与安全标记、密文报告、UC 秘密、结果、回执、审计、程序和备份；区分业务链路、浏览器入口、管理链路与本地文件。
2. 在现有 37 项上补充适用前提、标准版次、条款与页面、规范用语、负责阶段、验收用例和证据有效版本。原始分析保留，新结果作为追加记录。
3. 补充正式文本：43207、43206、32905、32907、32918.2、32918.5，以及适用认证加密文本。36624 当前仅确认元数据，取得全文后才能判断具体机制。设备接入时再补相应接口全文。
4. 核对 35275-2026、33560-2026 和随机性检测新旧版本的正式差异。已核对的实施日期分别为 2026-11-01、2026-12-01、2026-12-01；若迭代跨过日期，切换到适用版本并保存旧记录，不以草案代替正式文本。日期来源见[分析的官方来源](STANDARDS_ALIGNMENT.md#官方来源与本地证据索引)。
5. 先用现有只读就绪检查确定开发时段内的证书余量。到期时停止相应操作；新建隔离研发环境属于新环境初始化，不冒充在线轮换。

验收 S0.A：23 份材料与 37 项均有明确适用性和负责阶段；范围外材料保留原因；重要保护对象没有遗漏。验收 S0.B：缺全文、缺独立测试、外部条件未具备与已实测分别展示，缺证据不能显示“通过”。验收 S0.C：下面的设计决策形成可审查记录后，再实施相应信任或签名变更。

## S1 算法和协议边界验证

责任类别：密码实现与验证。主要涉及 `services/agility.py`、`services/signatures.py`、`services/native.py`、`native/agility.cpp`、`native/grid_crypto.cpp` 及验证工具。

1. 建立算法与参数登记，区分内部套件名称、标准算法名称、参数集、OID 或接口整数、编码、密钥用途、版本和来源。仅在标准适用的接口使用对应标识；未知或冲突的标识拒绝解析。
2. SM2 补身份预处理与 Z 值、参数、公钥点、签名整数范围和 DER 编码边界。SM3、SM4 补基础向量和必要边界。合法值、错误 ID、错钥、改消息、非规范编码、截断和超长输入分开验证。现有 CLI 与适配层共享 OpenSSL，继续标为集成互测；独立实现须另选、记录来源版本并真实执行。
3. 继续使用认证加密，补正 SM4-GCM 的标准归属。依据适用文本确定每密钥使用量和消息长度上限、计数器边界、重连换钥与错误状态；在双向、多 Source 场景验证 nonce 不重用及失败不发布。17964 不包含 GCM，不通过改用 ECB 来填补映射。
4. 复核双签 AND、SM2 增强、每段实际混合组、证书身份与授权对象的关联。跨实现握手测试记录组名与线缆标识；独立对端尚未取得时保留待验证。TLS 1.3、TLS 内 SM4 和 TLCP 分开描述。
5. 先界定自研适配层、密码库、进程边界和敏感安全参数。建立运行前检查与失败停止的工程要求；密码模块完整自测试与等级证明按 S5 的适用范围处理。

验收 S1.A：正式来源及选定向量具有摘要和版本，正确与异常输入的预期独立于被测输出。验收 S1.B：删去任一必需签名、错身份、错上下文、混合组不符、重放或认证失败均拒绝业务发布。验收 S1.C：登记能区分算法一致性、同库集成互测、独立实现互通和产品证明；PFDAM 参数项仍按自身证据判断。

## S2 身份职责和管理审计

责任类别：应用安全与运维。主要涉及 `services/sessions.py`、`services/governance.py`、`services/audit.py`、API、启动维护及完整性验证工具。

1. 区分业务操作者、密钥管理者和审计者；密钥更新、撤销、信任根变更、恢复和敏感导出定义独立权限。需要多人共管的操作以不同身份执行并关联同一操作单，不能由一个账户切换标签冒充多人。
2. 本地原型先验证角色权限与会话撤销、失败限制、敏感操作重新鉴别及审批流程。生产身份来源、人员入离岗和管理鉴别方式按真实部署确定；固定随机访问口令不称动态口令。
3. 扩展审计到登录失败、授权、轮换、撤销、配置变更、备份恢复、导出和异常。绑定操作者、操作对象、前后版本、结果及请求标识，不记录私钥、解锁口令或源明文。
4. 管理审计与业务 GW 检查点分清责任，保护新增审计链及其可信锚。发现截断、回滚、修改或缺少必要审计时，应暂停相应高风险操作并给出恢复入口。自签本地日志不能防御完全控制主机的管理员。
5. 程序完整性从普通源码摘要扩展为受信的批准清单与启动核对，覆盖原生库、配置、依赖及关键入口。批准清单或根的存放与更新权限必须独立说明；攻击者可同时替换清单和程序时不能据此证明来源可信。

验收 S2.A：每类敏感操作验证允许角色和拒绝角色，禁用账户及撤销会话即时阻止后续请求。验收 S2.B：单人不能完成定义为双人控制的操作，重复或过期审批不能复用。验收 S2.C：日志修改、截断、回滚、写入失败和程序替换有实际故障用例；审计锚和未覆盖范围可核对。研发账户流程与实际岗位制度执行分别留证。

## S3 密钥和信任生命周期

责任类别：密钥管理与协议工程。主要涉及初始化、签名验证、可信登记、角色启动和证据验证；新增托管和登记组件的边界先设计再实现。

1. 按用途登记 CA、TLS、ECDSA、ML-DSA、SM2、PFDAM 参数秘密、会话密钥和访问凭据。登记拥有者、允许操作、算法、密钥版本、有效期、状态及保管方式。签名、解密、会话用途不混用。
2. 将秘密保护与公钥可信性分别解决。研发可先设计口令解锁的软件托管方案，生产预留外部托管接口；解锁材料不写入仓库、日志或密文同目录。选定派生、包装和内存使用方式后记录威胁边界，不把加密文件视为抵抗主机完全失陷的保证。
3. 可信登记采用显式版本、授权签发者、完整性保护与防回滚状态；独立说明首次信任根如何可信导入及更新。新登记不能因为和公钥放在同一归档里就自动成为可信根。管理签名也保持相应必需算法的 AND 约束。
4. 先实现对象签名密钥和角色 TLS 证书的更新、撤销。任务固定使用的密钥版本、证书指纹和登记版本；激活、切换、崩溃恢复和失败停止具备事务边界。退休密钥只用于明确允许的在途或历史验证；撤销策略单独规定，不能自动回退到旧密钥。
5. 新多版本对象采用新 schema 和签名上下文，历史 V1/V2/V3 仍按原规范字节核对。区分“签名数学有效”“历史时点信任有据”“当前已撤销”，没有可信时点证据时不能推断撤销前已签署。
6. 备份策略按用途制定：会话密钥不归档；签名密钥不一律要求可导出；必须恢复的解密秘密有受保护备份与授权流程。销毁记录区分停用、逻辑删除、提供方删除和可证明清除。

PFDAM 参数秘密变更不是换一张签名证书：它影响 `param_id`、已有密文和恢复能力，另立方案分析；本轮不把它纳入自动轮换。CA 根更新也须有独立迁移与回退保护方案。

验收 S3.A：错用途、错版本、伪造登记、替换公钥、旧登记回滚、过期或撤销身份均按既定策略拒绝。验收 S3.B：真实完成一次正常切换与一次撤销，验证在途任务、新任务、重启和中断恢复；失败期间不降级。验收 S3.C：旧版本归档可按外部可信历史资料验证；缺根、缺历史状态或缺可信时间给出明确未决结论。验收 S3.D：错解锁材料及未授权读取失败，GW 仍无法接触 Source 明文与 UC 秘密。

## S4 业务存储和 UC 结果声明

责任类别：数据保护与证据工程。主要涉及 `services/storage.py`、各角色数据目录、schemas、签名服务、`services/evidence.py` 和扩展证据工具。

1. 逐类确定 Source 原始数据、UC 秘密、结果、凭据和归档的存储要求。需要机密性的对象采用版本化认证加密封装，绑定对象类型、拥有角色、数据集、密钥版本和格式；只由授权角色解密。PFDAM 业务密文与磁盘保护是不同用途。
2. 迁移先写新对象、核对、再切换引用，保留恢复途径。临时文件、错误日志、备份及进程崩溃后的残留均检查；普通文件删除不承诺不可恢复销毁。
3. 新建 UC 结果声明对象，绑定任务与授权摘要、算法及密钥版本、函数、时间窗口、整数单位或表示、计数、有效集合摘要、回执、快照及已认证来源引用。草案对象名为 `GRID_UC_RESULT_V1`，正式字段和上下文在实施前审定；它不是把既有 V3 结果字段重新解释为已签名。
4. UC 结果使用该业务套件必需签名的 AND 验证，发布与离线验证都核对预期任务及引用。平均值用确定的整数比值或等价规范表示，避免浮点归一化改写签名语义。不把性能、普通连接日志和来源说明文字悄然纳入已认证事实。
5. 长期归档保存必要公钥、证书、登记、状态及格式版本引用；区分本地时间、可信时间与缺失状态。算法迁移和保留周期先按对象制定；没有外部可信时间证据时不宣布长期有效性已完成。

UC 签名可以认证 UC 的声明来源与完整性，不能单独证明解密正确、源全集完整、读数真实或统计发布隐私。独立预期集合与整数和仍是研发正确性验收的必要条件。

验收 S4.A：错钥、改密文、改 AAD、错对象关联、未授权角色及备份替换均拒绝；失败不产生可用明文结果。验收 S4.B：修改结果、计数、单位、函数、时段、任务、回执或快照关联均被验证器拒绝，缺失必需签名也拒绝。验收 S4.C：真实迁移与中断恢复有记录，旧归档原字节及历史验证保留，导出物没有秘密或逐户原始明文泄露。

## S5 标准消息和密码产品接口

责任类别：标准互通与密码产品适配。此阶段按需求分支，未启用项保持条件适用，不为增加算法数量而引入新协议。

| 分支 | 启用条件和工作 | 验收条件 |
|---|---|---|
| SM2 标准消息 | 对接方要求完整标准消息，且已取得适用版全文；实现标识、ASN.1 与业务对象关联 | 双向互通、异常编码拒绝；封装前后规范字节不变，额外必需签名不被剥离 |
| 密码模块与自测试 | 明确承担模块职责，或使用具备相应证据的外部模块 | 边界、服务、角色、敏感参数和运行环境有对应依据；运行前与条件测试及错误状态实测；不凭页面按钮宣布模块认证 |
| SKF 与 SDF | 实际智能密码钥匙或密码设备及接口资料可用 | 分别核对接口版本、身份、密钥用途、错误码及签验互通；模拟器结果与真实设备结果分开 |
| 标准签验服务 | 实际提供或对接 38629 所述产品服务 | 核对证书、管理员鉴别、自测试、备份、日志、时间与标准请求响应；自定义业务 API 不能替代完整接口 |
| TLCP | 存在真实 TLCP 对端和明确接入场景 | 先设计隔离路径及身份、授权和证据绑定，再实测握手与双向业务；不把它当作现有 SAB 的自动回退 |
| 动态口令 | 真实身份方案选用相应动态口令机制 | 按适用全文核对生成、鉴别、时间或计数状态和重放拒绝；不能仅改固定口令的页面名称 |

验收 S5.A：启用前有适用版本全文、对端或产品信息、边界及验收协议。验收 S5.B：每个启用分支保存真实互通和负例，核对产品证明的准确版本与适用边界；通用接入代码不自动继承产品认证。验收 S5.C：未启用项保留条件和原因，SAB、双签及源和 UC 隔离没有因适配而削弱。

## S6 部署恢复和应急核验

责任类别：部署运维与恢复验证。先完成本地可重复演练，再按资源进行第二台物理机和真实设备测试。

1. 本地验证证书到期、签名密钥泄露、撤销、登记损坏、审计损坏、磁盘写入失败和受保护备份恢复。每项记录触发、检测、阻断范围、负责身份、恢复步骤和恢复后的完整性检查。
2. 恢复时保持根和登记的防回滚，记录恢复点及后续状态；用旧备份恢复不得重新激活已撤销密钥。备份没有相应解锁条件或审批时不能绕过保护。
3. 将浏览器入口、主机登录与远程管理单独纳入部署设计。当前回环 HTTP 不称全平台链路加密；远程浏览器和管理入口必须有选定的认证、受保护传输和访问边界，保持角色间既有链路约束。
4. 有第二台设备后，实测跨机角色身份、证书更新、访问边界、连接中断和恢复；清楚记录物理拓扑、网络和时钟来源。同机多 Source 结果不改名为多机部署。
5. 管理制度落实到具体密钥操作、岗位和应急记录；硬件或人员资源尚未具备时，保留部署待验证项。没有已确定的实际电网部署对象，不推导具体行业适用结论。

验收 S6.A：本地故障演练以真实状态变化完成，错误时停止受影响输出，恢复后重新完成身份、信任、集合及整数和核对。验收 S6.B：备份篡改、越权恢复、旧状态回滚和撤销后复活均拒绝。验收 S6.C：跨机、设备和制度执行有真实证据才关闭对应子项；缺少这些条件时只验收本地研发部分。

## S7 回归验收和持续检查

责任类别：测试验证与独立复核。每次涉及代码、配置或签名规范的变更都生成新版本，原有性能与测试记录保持原归属。

1. 每个阶段先运行与变化直接相关的正反用例；阶段冻结后做跨角色集成。最终候选运行既有回归与新增生命周期、存储、身份、结果声明、历史兼容和应急用例；不靠增加重复用例数量制造安全证据。
2. 检查 V1/V2/V3 原字节、历史证据和新版本对象的解析分离，避免新验证器把旧缺失字段补成安全保证。独立真值只在受隔离的验证侧使用，不能给 GW 放开读取权限。
3. 在新隔离目录、密钥和环境完成离线复验；密码、角色和存储路径实际运行。其结果继续限定为所测环境的工程证据。
4. 只读自检展示登记状态、证据摘要、对应代码版本和待验证项。已有标准项 `PARTIAL / NOT_EXECUTED` 不能凭本计划直接升级；代码变化使相关证据失效时提示重测。
5. 性能只在需要评价新开销时重测受影响配置。若对新版本重新提出规模结论，再运行对应完整系列，记录相同输入、预热、正式次数及资源；不把 V4.2 的 30 次系列搬到新版本名下。

验收 S7.A：每项实际结果有命令、工具与库版本、输入、源码和原生库摘要、预期、实际、退出状态及证据引用；验证记录与实现定义分开。验收 S7.B：启用范围的门槛均有有效证据或明确未决项，未决项不伪装为完成。验收 S7.C：更新 STATUS、NEXT、CRYPTO_REVIEW，研发验收、部署就绪和正式评估分别表述。

## 实施前需要定稿的设计

以下是本计划的设计工作，不要求现在提交最终材料或立即更换协议。每个决定都要写出字段或接口、信任前提、迁移、故障状态与反例，再实施关联阶段。

| 决定 | 规划方向 | 影响阶段 |
|---|---|---|
| 秘密托管与解锁 | 研发优先评估口令解锁的软件托管；外部设备为条件分支。包装密钥及恢复材料须独立保管，派生参数依据待取得文本与威胁分析确定 | S3、S4、S6 |
| 信任根与登记更新 | 独立可信导入、授权签发、单调版本和回滚阻断；归档内自带根不自动可信，完全主机失陷的边界保留 | S2、S3、S7 |
| 多版本和撤销语义 | 新任务只接纳当下授权版本；在途任务固定版本并制定退休/撤销处理；历史信任和签名数学有效性分开 | S3、S4、S6 |
| 新签名规范 | 多版本授权/回执新增 schema；UC 结果是新对象。所有字段、上下文、整数与平均值表示和必需算法集合先固定 | S3、S4、S5 |
| 时间和长期归档 | 本地创建时间只作为声明；可信时间来源与证书状态服务按实际资源确定，缺失时显示结论未决 | S3、S4、S6 |
| 标准接口与部署路径 | 先确定对端、现行版本和保留 SAB 的组合方案，再实现完整消息、TLCP、SKF/SDF 或签验服务 | S5、S6 |

这些决定不授权替换 PFDAM 数学、降低 SAB、自动切换纯国密业务或扩展 GW 的秘密权限。涉及实质密码方案变化时另行呈现具体候选和影响，由用户决定。

## 首轮工作清单和完成判断

首轮先完成 S0 的资产、标准与证据登记，以及 S3/S4 所需的设计草案；随后开展 S1 的高风险边界验证和 S2 的权限、重要操作与审计设计。此时不需要密码硬件，也不需要启动最终材料工作。

研发迭代完成的判断是：已选范围有真实实现、关键负例可拒绝、历史兼容可核对、证据与版本一致，剩余条件和研究问题清楚登记。多机部署、产品证明、制度执行和正式评估分别形成后续门槛，不用一个总“通过”掩盖范围差别。

参数安全 PENDING、低熵候选策略与特定条件下类别可识别、统计发布的小群体和差分查询风险、可信 UC 与不串谋假设，以及内层和证书的经典密码边界继续独立跟踪。没有依据时不预设发布阈值、差分隐私参数或新的安全证明。对齐工作的价值在于让团队方案的密码使用可解释、可管理、可核对，同时准确保留它的研究边界。
