# 密码标准对齐分析与研发改进清单

日期：2026-10-17。对象：当前 V4.2 本地研发原型。本文件是工程分析和迭代依据，不是正式密评结论、产品认证报告或最终参赛材料。

当前判断：我们的作品已经具备真实密码计算、授权约束和可核对的证据链；离系统层面的标准对齐，主要还缺密钥全生命周期、生产身份与证书管理、重要数据的存储保护、标准接口和运行管理闭环。不能把采用 SM2/SM3/SM4、通过若干向量或完成 77 项测试直接写成“符合全部密码标准”。

PFDAM 是本团队自己的前期研究方案。标准算法实现来自 OpenSSL、mcl 等组件，分别说明来源。标准对齐围绕团队方案的应用系统展开，不把国家标准算法称为团队发明。

## 密码实现和接口的具体分析

### SM2 的使用已有基础，格式与边界验证还不完整

`native/agility.cpp` 使用真实 SM2 密钥、SM3 和 EVP 签验接口；显式配置 ID，不依赖未知默认值。`services/signatures.py` 将对象类型和版本映射到不同上下文，使用可信角色密钥登记；普通业务保留 ECDSA AND ML-DSA，增强模式再 AND SM2。已有测试拒绝错误消息、错误公钥和错误 ID，并完成 OpenSSL CLI 与适配层双向验证。这些是有价值的正面证据，但 CLI 和适配层共享 OpenSSL 实现。

GB/T 35276 的重点定位为：第 5 章密钥对；第 6 章数据转换；7.1 密钥格式；7.3 `SEQUENCE { R INTEGER, S INTEGER }` 签名格式；8.1/8.2 身份预处理；9.4/9.5 签名和验签。相关内容在 PDF 第 5—9 页。

下一轮应补：标准曲线参数和公钥编码的逐项记录，按该版本第 5 章核对私钥范围；r/s 越界、非最短 DER、截断/多余字段、错误曲线、无效公钥点及字节转换边界测试；使用正式标准向量核对 Z 值与消息预处理；与另一独立实现互通。现有按对象类型设置 ID 是我们的协议约定，应固定并公开互通规则，不能据此声称已有真实人员身份认证。

GB/T 35275 讨论的是完整加密/签名消息封装，其第 5—7 章涉及 OID、数据类型和内容结构。现有签名值即使采用 DER，也不自动成为该标准的完整 `signedData`。保留内部规范 JSON 是可行的应用设计；当我们宣称标准封装或对接相关产品时，需要明确的标准消息适配层和互通证据。新适配必须继续绑定原始规范字节、算法集合、版本、角色和密钥 ID，不能为只输出 SM2 消息而丢掉普通业务要求的双签。

### SM4-GCM 的工程防护较完整，标准映射需要补正

现有实现固定 128 位 SM4 密钥、96 位 nonce 和 128 位认证标签；从实际 TLS 连接 exporter 导出方向分离的密钥；每连接使用递增序号；AAD 绑定帧版本、链路、发送方、接收方与序号。接收端检查上下文及序号，认证失败清除原生输出并拒绝使用。TLS 会话复用和 0-RTT 被禁用，避免将连接更新和 nonce 管理留给不清晰的复用状态。已有 RFC 8998 A.1 样例及错误密钥/nonce/AAD/标签、帧重放测试。

GB/T 17964-2021 第 5—13 章覆盖 ECB、CBC、CFB、OFB、CTR、XTS、HCTR、BC、OFBNLF，目录见 PDF 第 2—3 页。它没有 GCM；CTR 也不是完整 GCM。不能将“SM4-GCM 已按 GB/T 17964 全面验证”列为结论，更不应为了对照目录改用 ECB。

需要补充认证加密机制的适用文本和实现配置，GB/T 36624-2018 目前仅确认元数据，全文及具体适用机制待复核。GCM 的后续验收应包括每密钥使用量/消息长度上限、计数器边界、重连换钥、双向/多 Source 的 nonce 唯一性、认证失败后业务不发布，以及独立实现向量交叉核对。现有 RFC 向量通过只支持相应样例一致性，不代表完成全部模式测试。

### TLS 1.3、RFC 8998 与 TLCP 应分别记录

当前记录层明确使用 `TLS_AES_256_GCM_SHA384`，证书身份为经典 ECDSA，强制实际协商 `X25519MLKEM768`。增强业务帧在 TLS 内再使用 SM4-GCM。它不是 TLCP，也不是使用 `TLS_SM4_GCM_SM3` 的完整 RFC 8998 TLS 配置。

GB/T 38636 的范围明确包含记录层、握手协议族和密钥计算，不能由多套算法名称相同推出协议等价。后续如有真实 TLCP 对接需求，可增加隔离的互通适配或外部网关路径；应分别证明证书、握手和业务绑定，并保持普通业务 SAB 的最低保护，不将 TLCP 或纯国密实验入口作为自动回退路径。具体组合架构应先形成方案，再进行版本化实现。

现有混合组的国际依据已经更明确：[RFC 10024](https://datatracker.ietf.org/doc/html/rfc10024) 定义了 X25519MLKEM768。ML-KEM 和 ML-DSA 对应 FIPS 203、204。可以把这一点用于解释我们的迁移设计，但仍须区分：算法规范、混合组合协议、标准一致性测试、模块认证、内核安全和整系统安全。PFDAM 的配对/Paillier 内核和证书身份仍属于经典密码。

### 密钥管理应成为下一轮主要工程工作

当前密钥与证书由本地初始化产生。TLS 身份密钥、对象签名密钥和 PFDAM 秘密用途分离，Source 的证书及私钥独立；文件权限和 Landlock 边界已验证。今天的就绪检查支持上述当前状态。

但固定 epoch=1，可信公钥登记依赖受信本地文件，尚无在线轮换/撤销；秘密 PEM/JSON 文件的权限控制不等于受保护托管；没有受保护备份、恢复审批及销毁验证。直接新建运行目录会生成新的根与参数，这是一套新环境，不是在线轮换。

建议建立按密钥用途区分的登记与状态模型：拥有者、用途、算法/参数、版本、启停时间、状态、存储位置/保护方式、允许操作、审批和审计引用。覆盖 CA/TLS、ECDSA、ML-DSA、SM2、PFDAM 参数秘密、帧会话密钥和本机访问凭据。更新时新任务使用有效版本，历史验签按保存的历史信任和撤销策略处理，不能“换钥即全部历史失效”，也不能“撤销后新任务仍继续签名”。

备份与销毁按用途设计，不笼统要求所有私钥可导出；签名私钥、解密秘密和会话密钥的策略不同。通用文件删除不证明已经不可恢复地销毁，受保护托管也不能以“把加密口令写在同目录”代替。硬件产品接入和具体根密钥托管方式需纳入后续部署方案。

### 密码模块、自检与签验服务不是同一个概念

GB/T 37092 同时涉及软件、固件、硬件及混合模块。不能因没有 HSM 就断言软件模块必然无法对齐，也不能因有一个 `.so` 就称其通过密码模块认证。7.1—7.10 等条款涉及模块规格、接口、角色/服务、运行环境、敏感安全参数和自测试；7.10 的自测试不是让用户点击一次页面按钮。其要求涉及提供数据输出前的运行前测试、条件测试及失败后的错误状态/输出限制。模块整体等级也不能由某一个领域的实现直接推出。

我们的“安全自检”是原型检查：算法探针、密钥就绪、当前回执、链路与开放风险。它没有实现标准密码模块的全部内部状态机、独立运行前/条件自测试、模块安全策略或认证流程。未来应先界定自研适配层、密码库和外部产品的边界，再决定哪些职责由已验证产品承担。

GB/T 38629 第 5 章的功能还包括应用登记、证书更新/验证、备份恢复、日志与时间同步；6.4.2 的管理鉴别、6.4.3.2 的自检、6.7 和第 7 章的服务接口也应对照。当前本机业务账户不是该产品规范的完整管理员/审计员机制，自定义 FastAPI 路由也不是标准 ASN.1 请求响应接口。只有将其产品化或明确宣称提供该标准签验服务时，才应承担相应完整要求。

### 标识和文件保护要兼顾互通与业务语义

`V41_HYBRID_SM`、`SM2-SM3` 等是内部协议名称。GB/T 33560 的相关标识表、整数编码与 OID 不能靠字符串相近来对应。需要建立版本化字典，明确内部名、标准名、标准版次、OID/接口整数、参数集、用途与编码方式。未知标识应拒绝，不自造标准保留号。2017 版第 1 章明确为 PKI 体系，2026 版的差异须以正式全文核对。

GB/T 38541 的文件模型同时关注内容和属性，并允许应用系统以自维护方式组织属性、对属性进行密码操作并维护与文件的关联，因此 JSON 本身不是违反该指南的理由。我们已经做出的任务/政策/数据集/Source/快照/审计关联有直接价值。

剩余重点是：UC 发布的恢复结果没有被现有 GW 签名直接认证；源数据全集的真实性/完整性也没有由 Merkle 包含证明独立证明。可以设计新的、显式版本化的 UC 结果签名对象，绑定任务、函数、窗口、结果、计数、有效集合、回执、快照、数据来源和策略；它可以证明 UC 的结果声明来源及完整性，仍不是公开可验证解密或源读数真实性证明。公开结果的访问条件、小群体与差分查询风险继续单独研究。

长期归档还需要历史公钥/证书、签名时点与可信时间、撤销信息、保留周期和算法迁移方案。当前普通文件摘要、`created_at` 和本地公钥文件不自动提供完整长期有效性。性能、普通连接日志等辅助信息仍应显式标为未签名，不能为了界面整齐而冒充已认证事实。

## 下一轮研发顺序与验收条件

下表为分析提出的路线，不表示这些功能已经实现，也不授权改动 PFDAM 数学。涉及签名对象和信任语义的实现必须使用新版本，保留 V1/V2/V3 历史验证和原证据。

| 顺序 | 具体工作 | 可审查产物与验收条件 |
|---|---|---|
| 1 | 标准与保护对象登记 | 每项记录标准版本、适用对象、应/宜/可、条款/页面、状态、代码及证据；缺证据时不能显示通过；记录即将实施的版本 |
| 2 | 算法/参数/接口清单与标准向量 | 补 SM2/SM3/SM4 基础文本及适用认证加密文本；正确值、异常值、编码边界、ID 和跨实现测试分列；PFDAM 参数论证继续独立进行 |
| 3 | 密钥生命周期与可信登记 | 新旧版本并存、轮换、撤销、用途约束、证书状态和历史验签；旧钥新任务拒绝、历史任务按既定信任政策核对；重要操作有审批/审计 |
| 4 | 存储保护与结果声明 | 按对象区分原始数据、UC 秘密、口令、结果、归档的保护要求；篡改/错钥/未授权读取失败；UC 结果签名不能混成公开解密证明 |
| 5 | 运维身份与审计 | 密钥管理、密码操作、独立审计职责分开；记录登录失败、轮换/撤销、配置变更、导出/恢复与异常；审计锚定范围和未覆盖范围可检查 |
| 6 | 标准消息和产品适配 | 按业务需要实现 SM2 消息封装及标识映射；SKF/SDF/签验服务分别验证；不改变既有规范字节或丢失 AND 签名要求 |
| 7 | 外部设备与网络互通 | 如有设备资源，对接实际密码产品并核对其证书/适用版本/边界；真实多机、管理链路保护、必要的 TLCP/IPSec 单独验证 |
| 8 | 应急与部署核对 | 密钥泄露、CA 失陷、证书到期、审计损坏和备份恢复演练；将代码验证与制度执行、产品证明和正式评估分别留证 |

应优先补足实际安全控制与证据，不能只新增一个显示“符合标准”的页面。现有 `services/selfcheck.py` 的标准条款字段仍是 `NOT_EXECUTED`，属于程序内的既有标记；本次外部分析不自动改写为 `PASS`。后续界面可以展示适用性与缺口登记，但其整体结论仍应保留开放项。

## 对作品优势的准确表达

可以突出：团队自研细粒度密态聚合与标准密码外层结合；业务授权真正决定密文参与集合；正常业务强制双签 AND 和实际混合组，增强模式加入真实 SM2/SM3/SM4；V3 绑定多 Source 身份、数据时段与快照；回执、审计与独立集合/整数和能够分项复核；实验绑定源码和真实数据来源。标准对齐后，这些能力更容易按保护对象解释给密码方向评委。

不能使用的结论包括：“采用国密等于全系统符合国密标准”“OpenSSL 等于通过密码模块认证”“TLS 内使用 SM4 就是 TLCP”“使用配对就是 SM9”“随机访问口令就是动态口令”“数字签名回执就是电子签章”“Merkle 证明源全集真实完整”“GW 签名证明 UC 明文计算正确”“通过测试已经取得三级密评”“外层使用后量子算法使 PFDAM 内核也后量子安全”。

参数安全 PENDING、低熵策略/特定条件下类别可识别、统计结果发布隐私、可信 UC 和不串谋、经典身份、固定 epoch 及同机部署等既有边界继续保留。未来实际电网接入所需的行业标准、网络边界、设备与管理要求，应基于确定的部署对象另行分析。
