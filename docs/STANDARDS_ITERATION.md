# 密码标准对齐研发迭代

2026-10-17，用户授权目标模式执行标准对齐计划，并要求聚焦主要功能、避免琐碎扩展。实施范围为计划中可在当前研发环境实际完成的工程控制；条件接口、产品证明和物理部署按实际资源核对。最终材料与发布仍暂停。

## 核心设计

新增组件围绕秘密托管、可信登记和管理操作、UC 结果声明三个职责组织，复用现有业务流程与界面，不新建独立管理门户。PFDAM 数学保持原字节；SAB、必需签名 AND、混合组与 GW 秘密隔离保持。

秘密分角色保护。父协调进程属于可信管理边界，解锁受保护的托管根；子角色仅通过一次性继承管道接收本角色材料及公开信任锚，不继承管理员口令或其他角色秘密。角色的 Landlock 边界继续生效。磁盘上的秘密 JSON 使用版本化 SM4-GCM 封装，私钥使用 OpenSSL 加密 PKCS#8；不生成明文临时私钥。独立托管根保存在运行目录和代码仓库之外。

当前 Windows 上的 WSL 研发环境选用 Windows 当前用户 DPAPI 保护托管根，使用非交互桥接且不输出解锁材料。纯 Linux 路径要求显式提供解锁口令，使用固定配置的 scrypt 与认证加密；不能默默退回明文文件。这两种方式均依赖可信操作系统账户和协调进程，不抵抗完全控制同一账户或主机的攻击者，不称硬件托管或国密产品认证。[DPAPI 依据](https://learn.microsoft.com/en-us/dotnet/standard/security/how-to-use-data-protection)，[scrypt 依据](https://www.rfc-editor.org/info/rfc7914/)。

受保护根保存可信登记根的指纹及接受的最高登记版本，登记自身由独立管理签名密钥以 ECDSA 与 ML-DSA-65 双签。恢复旧运行目录时不能回退独立托管根中的最新状态；整个主机与托管根同时回滚不在该软件计数器的保证范围内。业务验证区分当前操作与历史签名核对，缺少可信签署时点不能证明撤销前已签署。

新业务签名规范采用显式 V4，多版本授权和回执绑定登记与密钥版本；V1/V2/V3 仍按原规范验证。UC 结果采用独立的新类型，认证规范整数结果、函数、计数与授权/回执/快照引用。结果签名认证 UC 声明，不是公开可验证解密或源全集真实性证明。

敏感管理操作使用现有本地鉴别基础扩展独立管理者和审批者身份、一次性审批及受保护审计。通过命令完成，不增加大规模前端功能。证书和对象签名密钥可以更新、撤销；PFDAM 参数秘密及 CA 根迁移保持独立设计，不纳入自动轮换。

标准映射、向量、负例、产品证明和正式评估分别记录。补充全文未取得、独立对端或设备缺失时保持待验证；不新增无需求的 SM9、ZUC、RFID 或电子签章实现。

## 标准依据与证据边界

补充取得5份已发布文本：GB/T32905-2016、32918.2-2016、32918.5-2017、36624-2018和GM/T0002-2012。来源为GmSSL作者维护的标准文档仓库镜像，保存来源URL、Git blob及SHA-256；与官方元数据区分，不能称官方签章分发件。增加44页选定OCR，关键公式和例子以页图复核；原包23份823页及原分析保留，未宣称所有条款逐页人工检查。

GB/T36624-2018第10.1节明确GCM，资料性C.5提供SM4例子，两个例子在本地实现及独立对端通过，解决了先前“17964没有GCM、归属待补”的具体缺口。每方向2^20帧、1GiB及单帧限制是保守应用策略，不写成该国标强制数字。SM4标准单分组例只在验证工具使用ECB，没有增加业务ECB配置。

43206/43207及GB/T32907的适用全文仍未取得；35275-2026、33560-2026和32915-2026仅核对官方版次/实施日期，正式全文差异待补。相应状态是缺全文或条件未具备。标准接口没有真实启用，因此不添加空壳CMS/TLCP/设备接口来增加功能数量。

应用自研职责为规范字节、算法组合、角色/用途/版本/数据关联、存储封装和状态管理；密码原语由现有OpenSSL/mcl实现，GmSSL仅为局部测试对端。父协调进程在可信管理边界内解锁独立根，工作进程只接收本角色材料后启用Landlock。完整模块内部自测试、故障攻击、物理安全及产品证明未由应用检查替代。
